# 02 · BetterMe 漏斗观察与取舍

参考入口：<https://betterme-pilates.com/first-page-brand-palette?flow=2117>

## 实际观察到的交互

本次使用 Computer 直接体验了入口及一段连续流程，确认了以下模式：

1. 首屏以年龄分段进入流程；选择后立即生成带 `order` 标识的 onboarding 会话 URL。
2. 流程采用“一屏一问”，顶部持续显示进度和返回入口。
3. 单选通常选择后直接推进；多选要求先选择，再点击 `NEXT STEP`。
4. 问题之间插入信任/解释页面，例如人群证明、计划为何有效、媒体背书，再用 `CONTINUE` 推进。
5. 问题不只收最终算法字段，还包含经验、体型、附加目标等用于个性化叙事的数据。
6. 页面底部持续提供 FAQ、条款、隐私、订阅与退款信息，降低付费焦虑。

### 明确未实测的部分

Computer 实测在“physical build”等中段问题处停止，没有把最终结果页/付费墙当作已亲眼验证。用户补充确认后续主要重复“选择 answer → 针对性页面”，最终生成结果页，且与题面要求类似。因此本计划的最终结果/付费闭环来自**题面 + 用户说明 + 工程推导**，不是对竞品末页的事实宣称。

用户已明确要求无需继续遍历长漏斗；本计划只借鉴已观察到的 UI 逻辑，不复制内容、素材或全部问题。

## 数据分类

| 类别 | 示例 | 是否持久化 | 本项目用途 |
|---|---|---:|---|
| 核心算法输入 | 年龄、身高、体重、目标体重、活动水平 | 是，强类型 | 计算与恢复 |
| 目标/偏好 | 减重、维持、增重 | 是，枚举 | health-v1 算法分支与文案 |
| 扩展个性化 | Pilates 经验、姿态/压力/柔韧性目标 | MVP 不做；stretch 才加版本化问答表 | 只影响叙事，不进入核心公式 |
| 流程状态 | 当前版本、已完成步骤、revision | 是 | 恢复、并发控制 |
| 计算结果 | BMI、TDEE、热量、日期、曲线 | 是，不可变快照 | 权限投影与审计 |
| 商业状态 | 订阅状态、有效期、支付事件 | 是，独立表 | 服务端鉴权 |
| 展示状态 | 动画是否播过、局部 UI 折叠 | 否或只存客户端 | 不污染领域模型 |

## 借鉴的 UI/产品原则

- 每屏只要求一个认知动作，降低放弃率。
- 明确进度，但不承诺不真实的精确完成时间。
- 用户每完成一步即出现保存反馈；网络失败时不假装成功。
- 在核心数据收集之间插入少量解释与信任内容，但不让营销页阻断恢复。
- 结果页先给有价值的 preview，再清楚说明被锁内容，而不是展示空白页。
- 付费前解释能解锁什么；模拟支付按钮明确写“Demo，不会扣款”。
- 条款、隐私、算法限制和非医疗声明可随时访问。

## 不照搬的部分

- 不复制 BetterMe 的品牌、图片、文案或完整题库。
- 不把所有营销答案混入算法；核心算法输入与扩展问答分层。
- 健康答案不写前端 localStorage，已保存进度只从服务端恢复。
- 不通过隐藏 DOM/CSS 实现付费墙；服务端根本不返回保护字段。
- 不把订阅状态放进客户端或长期 JWT 声明。
- 不创建真实订单或诱导用户认为会真实扣费。

## 对后端设计的直接影响

- 首次选择前后都必须存在可恢复 session；session 与 assessment 分离。
- Step 用稳定 `stepKey` 而非页面序号，问卷升级时旧数据仍可解释。
- `quiz_version` 固定步骤图；恢复时由服务端计算 `nextStep`。
- 核心字段使用强类型列；扩展问题等核心交付完成后才考虑版本化存储。
- 结果使用 preview/full 两套投影；客户端只负责显示，不负责权限判断。
- 支付完成后结果接口禁止共享缓存，并实时读取 entitlement。
